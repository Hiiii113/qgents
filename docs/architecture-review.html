1 · 工具结果只留一个形状：ToolResult

Strong
harness/runtime/ToolCallExecutor.java · sandbox/tool/CodingTools.java · sandbox/service/SandboxFiles.java · sandbox/service/SandboxCommands.java · memory/tool/MemoryTools.java · chat/tool/ChatHistorySearchTool.java · skill/tool/ActivateSkillTool.java · attachment/tool/ReadAttachmentTool.java · workspace/tool/WorkspaceTools.java · github/tool/GitHubTools.java · harness/runtime/AgentChatService.java
Before — 4 种失败形状
ToolCallExecutor / CodingTools / SandboxFiles
{"ok":false,"errorCode":"FILE_NOT_READ","error":"…"}
MemoryTools / ChatHistorySearchTool / ActivateSkillTool
{"ok":false,"error":"…"}
GitHubTools
{"ok":false,"error":{"code","message","nextAction","httpStatus"}}
WorkspaceTools.createWorkspace
{"ok":true,"workspaceId":"12","error":null,"repositories":[…]}
模型（唯一消费者）必须认识全部四种。
After — 一个 module，一个 envelope
ToolResult
ok(value…) · error(code, message, details…) · running(executionId…)
→ {ok, errorCode, error, details}
序列化只在 ToolCallExecutor 一处；异常→错误码的映射也在这里。

Problem: 面向模型的 interface 是 Map<String,Object>，ok/errorCode/error 的约定在 8 个模块里各写一遍，形状已经分叉。

Solution: 一个 ToolResult module，工具返回它；ToolCallExecutor 负责序列化和兜底错误码。

  • locality：失败形状只定义一次
  • leverage：30+ 工具共用一个 interface
  • interface 收窄，implementation 吸收 6 份 error()
  • 2 份重复的 safeMessage(Throwable) 一并消失

ChildRuns

loop、conversation、取消信号从外面传进来；三对 synchronized 留在里面。

Problem: 一次委派的状态分散在 WorkContext 与 AgentChatService 两边，三对嵌套 synchronized 由 4 个不同入口驱动；AgentChatService 因此有 17 个构造参数，测试要 mock 10 个协作者。

  • locality：竞态与通知逻辑一处
  • interface：15 → 5
  • 测试跨同一个 seam 验证取消与续接
  • 删掉 AgentChatService 里 4 个结算方法
这是六个候选里风险最高、也最能改变形状的一个：并发状态可以重构，竞态语义不能变；现有的 mock 测试无法证明并发正确，先把状态机搬到 seam 后面再补测试。

3 · 消息视图与游标只留一份：MessageViews

Strong
chat/service/MessageService.java (535 行) · common/dto/KeysetPagination.java · attachment/service/AttachmentService.java

send

enrichAttachmentPreview ← 每条附件消息查一次库
cursor_… (MessageService 私有) ✗ scope|id (KeysetPagination)

After — 组装一次
MessageViews

KeysetPagination.keysetPage(rows, size, "group-messages:"+groupId, …)

Problem: 三个 toResponse 重载和附件预览在 4 条路径各走一遍；列表路径每条附件消息单独查库（N+1）；消息游标是 MessageService 私有的一套 base64，和共享的 KeysetPagination 不通用。

Solution: 一个 MessageViews module 承担行→视图的全部组装并批量取依赖；分页改用 KeysetPagination，scope 绑定 groupId。

  • 一次批量查询代替 N 次
  • 一个游标规则，附件/团队/项目通用
  • 发送、列表、单条共用同一组装
  • 测试只对 assemble 断言一次

Problem: 角色推导写了两份（TeamService、AuthService），ProjectService 又复制了一套团队查询与管理员校验；18 个类提到 TEAM_OWNER / PROJECT_ADMIN，没有一个 module 能回答「这个人在这个团队/项目里是什么角色」。

  • ProjectAccessServiceTest 成为唯一 seam
  • 删掉 ProjectService 里 5 个复制的团队方法
  • 团队管理员边界有单一测试面
最近三次提交（团队管理员、项目管理员、权限边界）都在这一片；这也是它值得先于其他团队/项目重构的原因。

Speculative

  • 「选择变化要落库」留在 harness 内
  • 测试直接断言会话状态
  • 合并 WorkspaceSelection 这一层薄包装

6 · 附件类型从字符串变能力：AttachmentKind

Worth exploring
attachment/service/AttachmentService.java · attachment/tool/ReadAttachmentTool.java · attachment/web/AttachmentResponseFactory.java · chat/service/MessageService.java
Before — 一个集合，四道分散判断
IMAGE TEXT CODE PDF UNSUPPORTED
classifyPreviewType → AttachmentService（唯一产出点）
"IMAGE".equals → ReadAttachmentTool 分支
"TEXT"/"CODE" → AttachmentResponseFactory 的 Content-Type
"UNSUPPORTED" → previewable 判定（info / messagePreview 各一次）
"TEXT"/"CODE" → readTextChunk 的守卫
新增一种类型要改 4 个文件。
After — 枚举带能力
AttachmentKind
readableAsText · readableAsImage
previewable · responseContentType
callers 只问 kind，不再比对字符串。

Problem: 类型是 5 个字符串常量，但「能不能当图片读／响应用什么 Content-Type／能不能预览」的判断分散在三个模块；新增类型要同时改 4 处。

Solution: AttachmentKind enum 带能力，分类与能力判断一起收进这个 module，调用方只问 kind。

  • locality：类型集合与能力一处
  • 新增类型只改枚举
  • 预览判定不再重复两次
  • ReadAttachmentTool 的 if 分支消失
Top recommendation

先做 1 · ToolResult

六个候选里唯一「一天能落地、之后每个候选都变小」的一个：它先把面向模型的 interface 收成一处，后续 ChildRuns 的 ConversationTools、MessageViews、WorkspaceTools 都少写一份错误形状。C2 改变形状最多，等 C1 落地后再动。

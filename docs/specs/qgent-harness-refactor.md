# Qgent 与 Harness 架构重构需求规格

- 日期：2026-10-11
- 状态：产品与架构方向已确认；本次整理需求，尚未实施运行代码。
- 范围：固定 Qgent 入口、临时子 Agent、执行环境与生命周期、领域分包、Skill/Memory、项目级 GitHub 能力，以及后置的实时事件整理。
需求编号仅用于文档追踪，不引入产品内 Task、任务编号或任务状态机。

## Problem Statement

用户希望通过聊天中的一个助手完成讨论、分析与开发工作，不希望为了不同任务维护多个仅提示词不同的永久 Agent。现有系统仍把默认角色、自建 Agent、审核、头像昵称、群成员、消息作者及执行身份绑定在一起，增加了配置和理解成本。

主 Agent 应能根据工作需要自动委派临时子 Agent，子 Agent 可以分析或修改代码。现有同步递归委派、共享 Workspace 选择状态和根运行立即释放环境的行为，无法直接支持后台协作。

当前目录虽然按业务领域划分，但聊天 module 仍组装模型所需的 Skill/Memory，Agent 工具包混放多个领域的能力，Workspace 的持久资源管理又分散在 Sandbox。实现新行为时，必须同时解决职责归属，不能只搬文件或增加转发。

## Solution

用户只面对固定 Qgent。Qgent 根据任务目标决定自己完成还是委派一层后台子 Agent，并在当前聊天组织和返回成果。团队通过项目规则、Skill 和 Memory 提供约定与知识，GitHub 在项目级默认开启，导入仓库后可用。

### R01 — 固定 Qgent 聊天身份与永久 Agent 管理删除

**目标：**用户只需认识一个固定助手，临时子 Agent 不成为产品中的可管理角色。

**需求与验收：**

- 用户侧只保留名为 Qgent 的助手，不开放名称、头像或独立提示词编辑。
- 删除默认 GENERAL/CODING 区分、自建 Agent 的创建、编辑、审核、发布、上下线和头像上传等专属入口、业务契约及数据结构。
- 删除永久 Agent 管理时，同步清理团队初始化、团队清理、群成员、邀请、消息作者与名称查询中的旧身份依赖。
- 默认群和新建群沿用已经确认的访问、成员与邀请规则；Qgent 作为唯一助手仍可在适用群内被邀请或提及，临时子 Agent 不进入成员候选。
- 提及仍通过对象类型和标识表达，不靠昵称文本推断；普通消息和用户提及不启动 Agent。
- 消息提交后，显式提及 Qgent 启动一次根运行；相同消息的幂等重试不重复启动。
- Qgent 回复、消息读取、回复关系、未读和用户提及通知保持可用。
- 后端、前端真实页面、类型、查询、Mock、测试和建表脚本同步修改；不能只删管理页面，也不能先删除仍被引用的永久身份表。
- 固定聊天身份与 AgentRun 的执行标识分别表达；保留内部执行记录，不为替代永久身份再建一套可管理角色。

### R02 — 根运行与子运行的生命周期及资源所有权

**目标：**后台协作不会丢失运行状态，也不会提前销毁仍在使用的环境。

**需求与验收：**

- 根运行和子运行共用项目自己的 loop，继续通过 Spring AI 接入模型。
- 有工具调用时执行工具并继续；无工具调用的有效文本结束当前 loop；保留轮次上限、失败和取消行为，不引入 finish 工具或强制工具选择。
- 根运行拥有整次工作的共享环境、Workspace 写租约、已打开环境集合及整体取消归属。
- 每个 Agent 独立拥有对话、子任务指令、选中 Workspace、目录状态及自身运行结果。
- AgentRun 创建、状态变化、终态和资源收尾由 Harness 的执行生命周期 module 统一管理，不散落在聊天或业务工具中。
- 主 Agent 的一次模型 loop 结束与根运行资源可释放分别判断；不得为了保留环境引入独立 Task 业务。
- 需要等待的子运行、工具调用和命令完成或停止前，不得释放它们仍在使用的根环境。
- 正常结束、失败和取消均有收尾路径；释放 Sandbox、保留 Workspace，初始化失败时释放本次已取得的资源。
- 按触发消息停止执行的既有授权规则保留；根取消传播给所属子运行，停止继续派发，并按实际执行生命周期结算。
- 工具与命令记录关联实际调用的根或子 AgentRun 和 Workspace，不能把全部子运行记成根运行。
- 一次运行成功只代表本轮执行正常结束，不宣称用户长期目标已全部完成。

### R03 — 一层后台委派、等待、消息、停止与续接

**目标：**主 Agent 可在必要时分担工作，用户不需要手动组织多个助手。

**需求与验收：**

- 主 Agent 根据任务需要自主决定是否委派，不强制计划、编码、测试、审查等固定阶段。
- 委派创建临时子 Agent，不从团队永久 Agent 列表中选择，也不要求用户提前配置角色。
- 子 Agent 可以承担分析、检索或实际代码修改，任务类型不固定为只读审查。
- 启动子 Agent 后返回可操作的标识，主 Agent 不必同步等到子任务完成才能继续。
- 支持同时运行多个子 Agent，运行数量有界；限额通过正常工具结果反馈，不静默丢弃工作。
- 子 Agent 完成或失败时向主 Agent 交付结果或失败信息，主 Agent 可按需要等待并使用结果继续工作。
- 主 Agent 可补充要求、停止某个助手，或继续同一个助手的对话；停止单个助手与取消整次根运行分别表达。
- 只允许主 Agent 派出一层子 Agent；子 Agent 不能继续派生，相关递归代码和配置删除。
- 子 Agent 的过程与结果用于主 Agent 协作，主 Agent 统一向当前聊天组织成果，不恢复永久 Agent 的成员身份。
- 后台运行使用现有进程内执行机制，不引入内部 HTTP、数据库轮询或新的任务调度产品。

### R04 — 独立对话、动态子任务提示词与对话续接

**目标：**每个助手获得完成子任务所需的信息，同时减少无关上下文。

**需求与验收：**

- 通用工作方式由系统指令维护；项目差异由项目规则、Skill 和 Memory 提供，不恢复 Agent 配置页。
- 主 Agent 自主组织临时子 Agent 的提示词、任务目标、修改范围、必要背景和期望返回内容。
- 新子 Agent 默认从独立对话开始，不复制父 Agent 的整个模型历史或群聊。
- 子 Agent 可以按当前用户和项目的权限读取相关聊天、项目资料、Skill 和 Memory；独立对话不等于失去必要能力。
- 继续同一子任务时可复用子对话及已获得的上下文；不能每次补充指令都无提示地重建一个空白助手。
- 父子对话中彼此后续新增的内容不会因为共享环境自动混入；必要信息通过明确的任务或消息交付。
- 对话续接服务于当前执行协作；跨根运行恢复子 Agent、完整会话 fork 和冷恢复不作为本轮完成条件。

### R05 — 默认共享环境、独立目录选择与按需 worktree

**目标：**多个助手尽量在同一环境协作，需要隔离修改时再创建独立检出目录。

**需求与验收：**

- 纯问答、聊天检索、Skill/Memory 读取及不依赖代码目录的远端操作不启动 Sandbox。
- 首次真正需要代码环境时才准备 Workspace 并启动 Docker 沙箱；未选择时新建，已选择时复用。
- 同一根运行内，主 Agent 与子 Agent 默认共享根环境及代码目录，不按助手数量自动创建沙箱。
- 子 Agent 启动时获得适合任务的初始 Workspace 和目录；后续各自切换不会修改其他 Agent 的选择状态。
- 根运行统一跟踪实际打开的 Workspace 和环境，确保并发首次准备仍只初始化一次。
- 主 Agent 负责划分修改范围；可能发生文件重叠时可选择串行处理或按需使用 worktree，不假设共享目录自动解决冲突。
- worktree 是独立检出目录，通常关联另一分支；有需求时尽量在同一沙箱环境内创建，不为每个子 Agent 自动建分支或 worktree。
- 支持在工具执行中选择 worktree 所在目录；创建、使用和汇总由 Agent 按任务决定，不强制新增专用 worktree 管理平台。
- Workspace 领域拥有持久资源、访问和租约规则；Sandbox 拥有容器、路径约束、文件和命令执行；跨领域根环境编排属于 Harness。
- 会话复用、初始化失败清理、租约续期与释放、活动环境归属等现有有效行为随职责迁移保留。

### R06 — Harness 与领域工具、上下文的分包归属

**目标：**修改一种业务能力时，规则与验证集中在所属 module，不必追踪整个执行入口。

**需求与验收：**

- 删除永久 Agent 管理领域后，执行能力集中于 Harness，而不是把旧 Agent 包整体改名。
- Harness 内按真实职责划分运行、上下文、执行生命周期、工具适配和持久记录；不为目录完整而创建薄转发。
- 聊天触发与执行取消的 adapter 归 Harness 的集成职责；聊天事件和消息规则归聊天领域，避免聊天核心直接依赖具体执行 implementation。
- 模型输入的选择和跨领域组合归 Harness；聊天领域负责消息读取、转换与群访问规则。
- Skill 激活和内容读取归 Skill；Memory 查询和操作归 Memory；不让聊天 module 继续拥有它们的模型使用规则。
- Workspace、GitHub、聊天历史及 Skill 等领域工具留在所属领域，Harness 只组装和执行。
- Spring AI callback、并行标记及委派控制属于 Harness 的工具适配；附件内容与多模态装载属于附件领域。
- GitHub 项目配置与仓库授权不依赖已删除的 AgentEntity 或永久 Agent 开关。
- 不引入通用插件市场、全新工具注册平台或另一套编排框架。
- 通过现有行为 interface 测试迁移结果，不把类名、包名或私有方法组织方式作为产品验收指标。

### R07 — 项目规则与 Skill 的维护、可见范围和按需加载

**目标：**团队维护工作方法和项目约定，Qgent 在相关工作中按需使用。

**需求与验收：**

- 保留项目 Skill 管理与首次发布审核，不因删除 Agent 审核而删除 Skill 审核。
- 创建者或项目管理员可修改草稿、审核中、被拒绝和已发布 Skill；已发布内容修改后立即生效，已下线内容不可编辑。
- 创建者可下线自己已发布的 Skill，项目管理员可下线项目已发布 Skill。
- 普通成员只查看自己的 Skill 和已发布共享内容；管理员可额外查看用于审核的未发布共享内容，不能因此读取他人私有内容。
- 私有 Skill 和管理员创建的共享 Skill 直接发布；普通成员创建的共享 Skill 保留草稿、提交审核流程。
- 模型先获得适用的 Skill 目录，再按需读取正文；不把全部 Skill 正文放进每次提示词。
- 主 Agent 和子 Agent 通过同一领域能力获得相关 Skill，预算和加载状态不意外串到另一个独立对话。
- 项目规则不以自建 Agent 提示词作为载体；本轮不要求新建独立的规则编辑产品或数据模型。
- 标准 Skill 包导入、脚本执行及资源打包尚未形成明确实施决策，不作为本需求的默认扩展。

### R08 — Memory 的 Agent 操作工具与按需使用

**目标：**用户可以通过聊天让 Qgent 查询、记录和更新项目知识，而不是只能使用管理页面。

**需求与验收：**

- 提供 Agent 可调用的 Memory 查询、读取、创建和更新能力，以及既有状态规则允许的相关操作。
- 主 Agent 与子 Agent 都可按子任务使用 Memory；执行沿用触发用户的项目权限，不因 Agent 身份绕过可见范围或审核。
- 复用当前 Memory 的草稿、审核、批准、拒绝和归档规则；状态不允许编辑时返回真实限制，不静默覆盖已批准内容。
- 保留用户管理入口，Agent 操作与用户操作共用业务规则，不复制一套互相不一致的实现。
- 通过相关内容和预算控制输入，不无差别注入全部历史知识；有效项目规则与已确认事实按需要使用。
- 对创建、更新或受限操作返回实际结果，让主 Agent 能说明记录是否成功以及当前状态。
- 不恢复独立的 AI 沉淀按钮或草稿生成入口，AI 操作从聊天中的工具调用完成。
- 不将一次临时推测或尚未确认的架构建议冒充已确定项目事实。

### R09 — 默认开启的项目级 GitHub 能力与聊天操作

**目标：**项目导入仓库后，Qgent 就能按用户要求操作仓库与 PR，无需逐个配置助手。

**需求与验收：**

- GitHub 能力采用项目级开关，默认开启；删除 Agent 级开关与临时子 Agent 的独立凭证配置。
- 项目显式导入仓库后，Qgent 和子 Agent 可在当前项目导入范围内使用 GitHub 能力。
- 未导入仓库、开关关闭或 App 授权不可用时返回真实原因；不影响普通 IM、问答和无 GitHub 依赖的 Harness 工作。
- 保留团队 GitHub App 安装、回调、授权和项目多仓库导入，沿用按导入仓库取得短期凭证的机制。
- 不恢复个人 OAuth、凭证引用或部署 Token 模式。
- 导入不自动 clone、创建分支、分配 Workspace 或执行 Git 交付。
- Agent 按任务选择仓库；未指定基线时 clone 使用远端默认/base 分支。
- 用户可通过聊天要求查询 PR、push 或创建 PR，并收到实际结果和链接，不必到其他页面操作。
- commit、push、PR 由 Agent 根据用户任务目标决定，不引入后台自动交付或额外强制阶段。
- 前端项目能力配置、后端能力判断、工具注册及 Mock 同步迁移；必要时完成真实 GitHub 联调，不能以编译通过替代链路验证。

### R10 — Sandbox 执行语义保留与局部职责收拢

**目标：**架构整理不破坏已具备的文件操作、长命令和执行证据。

**需求与验收：**

- 继续使用单个 Spring Boot 应用内的 Sandbox module；用户命令在 Docker 内运行，不恢复内部 HTTP、双模式调用或宿主机回退。
- 文件读取保留行号窗口、搜索保留路径/行号/正文，截断明确；工具失败不能被解释为无匹配。
- 文件创建、替换、准确文本编辑和版本检查继续由 Sandbox 执行，文件版本由系统保存。
- 文件工具保持同步；长命令保留执行句柄、短等待、有界输出、字节游标、继续读取和取消。
- 非零进程退出码与基础设施执行失败分别表达，工具执行完成不等于构建或测试成功。
- 保留工具有界并行、串行屏障、结果按模型调用顺序回传及执行身份传递。
- 保留命令的线程池、进程内完成通知、实际 AgentRun/Workspace 记录，以及工作目录外保存完整输出的行为。
- 根运行结束前等待或停止活动命令；子 Agent 后台化不能绕过根环境的收尾规则。
- Sandbox 的会话、租约绑定、句柄归属和命令状态翻译具有实际职责，不按“链路长”直接删除。
- 单实现 interface 与重复结果翻译可以局部合并，但不能将命令和文件协议整体重写列为后台委派的前置条件。
- 保留本地磁盘/OSS 附件与 Docker/Fake runtime 等有实际 implementation 差异的 adapter；本轮不改变其产品使用约定。

### R11 — realtime 内部持久发布与连接传输拆分

**目标：**实时事件的发布与连接行为可分别理解和验证，不扩散到业务调用方。

**需求与验收：**

- 在 realtime module 内分开事件持久发布/事务规则与连接传输的内部职责。
- 保留事务提交后投递、新事务重试、事件顺序及业务可见范围。
- SSE 继续复用共同的游标校验、连接计数、心跳和 pump，不按项目、团队、通知复制三套机制。
- WebSocket 与 SSE 继续承担既有传输能力，通知与聊天调用方不需要理解连接内部细节。
- 测试通过发布和连接的行为 interface 验证，不以反射私有 pump 或测试专属构造器作为主要验收面。
- 不引入通用事件总线，不为这次 Agent 重构顺手重写通知、推送或团队业务。
- 本需求后置，可以独立实施，不阻塞 Qgent 与后台子 Agent 的核心交付。

## User Stories

1. 作为项目成员，我希望只看到一个固定 Qgent，以便不必判断应该选择通用还是 Coding Agent。
2. 作为项目成员，我希望直接提及 Qgent 开始工作，以便在现有聊天中协作。
3. 作为群成员，我希望普通讨论和提及同事不会启动模型，以便清楚区分讨论与执行。
4. 作为发送者，我希望消息重试不重复启动执行，以免产生重复修改。
5. 作为群成员，我希望固定 Qgent 的回复、姓名和未读正常展示，以便跟踪讨论与成果。
6. 作为项目成员，我希望新群仍按自己的成员名单管理访问，以便保持既有协作范围。
7. 作为团队维护者，我希望无需维护永久 Agent 角色、审核和头像昵称，以便减少管理负担。
8. 作为提出工作请求的用户，我希望 Qgent 自己决定是否委派，以便简单任务无需多 Agent。
9. 作为提出开发请求的用户，我希望子 Agent 能承担实际编码，以便分担可独立完成的工作。
10. 作为用户，我希望主 Agent 启动助手后还能继续工作，以便利用独立任务的并行机会。
11. 作为用户，我希望助手数量有界，以便执行不会无限扩张。
12. 作为用户，我希望助手完成或失败的结果能交回主 Agent，以便获得真实的统一成果。
13. 作为用户，我希望主 Agent 能补充助手要求或让它继续工作，以便修正和完善子任务。
14. 作为用户，我希望可以停止整次执行，以便不再进行不需要的操作。
15. 作为主 Agent，我希望可以停止单个助手，以便保留其他仍有价值的工作。
16. 作为项目维护者，我希望只存在一层委派，以便理解运行关系和资源归属。
17. 作为主 Agent，我希望自主组织助手提示词和任务，以便针对当前问题安排工作。
18. 作为子 Agent，我希望得到明确任务与必要背景，以便完成工作而不读取无关整段历史。
19. 作为主 Agent，我希望继续同一助手时保留其对话，以便无需重复传递已经确认的信息。
20. 作为用户，我希望子 Agent 切换目录不会影响主 Agent，以便并行工作互不改变选择状态。
21. 作为用户，我希望无需代码环境的问答不创建沙箱，以便保持轻量使用。
22. 作为用户，我希望首次需要代码时才准备环境，以便资源按实际需求分配。
23. 作为用户，我希望助手默认共用同一环境，以便避免重复准备仓库和依赖。
24. 作为主 Agent，我希望需要隔离修改时能在同一环境创建 worktree，以便协调分支和文件修改。
25. 作为用户，我希望助手和命令结束前环境不会被释放，以便已启动的工作能正确收尾。
26. 作为用户，我希望运行结束保留 Workspace，以便后续工作复用代码与成果。
27. 作为维护者，我希望内部记录指出实际执行的 AgentRun 和 Workspace，以便核对结果。
28. 作为团队维护者，我希望在项目规则和 Skill 中维护工作方法，以便不同任务共享有效约定。
29. 作为 Skill 创建者或管理员，我希望既有编辑、发布和下线规则继续生效，以便团队内容管理不被 Agent 重构破坏。
30. 作为普通成员，我希望只看到允许访问的 Skill，以便保持私有与共享内容的区别。
31. 作为 Qgent，我希望按需读取 Skill 正文，以便不占用无关上下文。
32. 作为用户，我希望通过聊天查询、记录和更新 Memory，以便知识维护融入工作过程。
33. 作为项目维护者，我希望 Agent 遵循 Memory 权限及状态规则，以便不绕过既有审核。
34. 作为用户，我希望项目导入 GitHub 仓库后即可使用相关能力，以便无需配置每个助手。
35. 作为项目管理员，我希望能在项目级关闭 GitHub 能力，以便统一管理当前项目。
36. 作为用户，我希望在聊天中查询 PR、push 和创建 PR并收到实际结果，以便不切换到其他操作入口。
37. 作为用户，我希望 GitHub 不可用时仍能聊天和使用其他 Harness 能力，以便能力解耦。
38. 作为用户，我希望长命令可以继续读取和取消，以便处理构建与测试。
39. 作为用户，我希望明确区分测试失败和执行机制故障，以便判断下一步处理。
40. 作为维护者，我希望运行规则、模型上下文和业务工具各有明确归属，以便修改集中且可验证。
41. 作为维护者，我希望实时事件继续正确过滤、投递与续传，以便内部拆分不改变用户体验。
42. 作为维护者，我希望每项重构能以行为验收并独立理解，以便避免不可用的半截提交。

## Implementation Decisions

- 已确认的领域分工：聊天拥有消息和固定 Qgent 身份；Harness 拥有 loop、AgentRun、后台委派、上下文组装和根资源生命周期；Workspace 拥有持久资源、访问和租约；Sandbox 拥有容器、路径约束、文件与命令执行。
- Harness 按实际需要使用 integration、runtime、context、service、tool、entity、mapper 等职责分包；不新增没有实际职责的 module。
- 业务工具属于聊天、Skill、Memory、Workspace、GitHub、附件等所属领域；模型工具 callback 和并行执行适配属于 Harness。
- 先分开根运行共享状态和各 Agent 独立状态，再实施后台委派。不能仅把现有递归调用提交到线程池。
- 一层委派是产品约束，替代当前可配置的多层递归；同时运行数量和 loop 轮次保留有界限制，具体参数值在实施时沿用或确定，不伪装为已经确认。
- 新子对话独立，继续同一子任务可续接；不采用完整父对话 fork。
- 资源释放必须与助手和命令的实际生命周期协调。根运行状态、子 loop 终态与用户长期目标分别处理。
- 永久 Agent 身份结构删除时，群内 Qgent 的可用状态、结构化提及和消息发送方需要改为固定身份表达；具体字段及标识编码在实施时选择，不预设新的永久 Agent 表。
- 数据库与代码按当前目标重构，不建立历史迁移或兼容机制；建表脚本同步更新不等于授权删除真实数据库或 Workspace。
- 项目新增或承接 GitHub 开关，默认开启；团队 App 授权、项目仓库导入和仓库级短期凭证机制保留。
- 聊天请求只携带基础 IM 字段；不增加仓库、分支、Workspace 或 Sandbox 执行参数。
- Skill 与 Memory 使用已有内容管理权限和状态规则；不为了 Qgent 统一入口重新发明审核。
- Sandbox 的运行身份、租约、长命令和结果语义保留；文件与命令的局部契约整理按实际收益处理。
- realtime 整理限定在内部 seam，不升级为新消息总线或产品调度系统。
- 测试与生产调用跨同一个行为 interface；必要的内部 seam 用于执行生命周期和外部依赖 adapter，不为测试反射而拆分纯转发。
- 本轮不预设新方法名称、线程池设计、事件载荷字段或工具参数 schema；它们属于实施设计，需满足以上验收条件。

## Testing Decisions

### 验收面

以下为基于已确认行为整理的验收方案。优先使用既有 seam，不要求每个内部类新增一套镜像测试。

| 验收面 | 覆盖需求 | 关键场景 | 既有测试参考 |
| --- | --- | --- | --- |
| 聊天触发、群成员、回复与取消 | R01、R02、R09 | 普通消息不触发、结构化提及、幂等重试、固定身份、群权限、真实成果返回 | MessageSentListenerTest、ProjectChatTest、ChatComposer 测试 |
| Harness 执行生命周期 | R02～R05 | 后台返回、结果交付、续接、单层限制、有界运行、独立选择、根取消、最后一个使用者结束前不释放环境 | AgentChatServiceTest、AgentRunServiceTest |
| 模型 loop 与工具执行 | R02、R03、R06、R10 | 工具后继续、有效文本结束、轮次上限、并行屏障、结果顺序、实际身份传递 | AgentLoopTest、ToolCallExecutorTest |
| 上下文与领域工具 | R04、R06～R09 | 聊天/Skill/Memory 可见范围、按需加载、输入预算、子任务必要背景、GitHub 项目开关 | ContextServiceTest、ActivateSkillToolTest、ChatHistorySearchToolTest、GitHubToolsTest |
| 环境和命令 | R02、R05、R10 | 单次初始化、失败清理、租约、句柄归属、文件版本、输出游标、退出码、取消 | SandboxSessionManagerTest、SandboxCommandsTest、ToolExecutionServiceTest、CodingToolsTest |
| 实时事件 | R11 | 提交后投递、接收人过滤、重连游标、事务重试、连接释放 | EventServiceTest |

### 测试原则与完成条件

- 验证用户可见结果和执行 interface 的行为，不断言重构后的私有方法、内部调用次数或类组织方式。
- 使用可控模型和依赖 adapter 重现关键调度顺序，不用固定睡眠来猜后台任务完成时间。
- 背景任务场景必须证明主 Agent 可以先获得启动结果，而不是只验证最终文本相同。
- 环境隔离场景必须证明子 Agent 切换选择后父 Agent 仍使用原目录，并证明环境不会提前释放。
- 权限与状态限制沿用现有业务规则；覆盖可操作与明确拒绝两类结果。
- 将现有同步委派的相关测试改为新行为测试，不用旧断言阻碍已确认变更。
- 后端代码改动完成编译及相关可执行验证；涉及前端时完成对应测试、lint 和构建。
- Docker、数据库、模型与 GitHub 的真实联调分别记录实际执行条件和结果；未执行不能声称完整链路通过。
- 真实服务测试先核对目标与授权，不以本规格为清空数据库、工作区或操作生产的授权。
- 相关验证通过后按独立可理解、可回滚的粒度提交，不推送；无法独立成立的前后端与结构改动合并提交。

## Out of Scope

- 永久角色市场、自定义 Agent 配置页、多层递归、强制 plan/coding/review 流水线。
- 独立 Task 业务、任务看板或对外 AgentRun 使用统计与运行记录查询。
- 每个助手自动独立沙箱、自动 worktree、自动分支，以及新的工作区调度平台。
- 子 Agent 跨根运行冷恢复、完整父对话 fork、多提供商或多模型路由平台。
- 标准 Skill 包导入、资源打包和脚本执行平台：此前讨论过方向，但未确认本轮实施方案。
- 新建独立项目规则管理产品或修改 Memory 的既有审核状态策略。
- 新的 RAG、代码索引、流式模型输出、用户运行中追加聊天输入与历史压缩；主 Agent 给子 Agent 发消息属于 R03，不等同于这些能力。
- 新增 Diff/MR 卡片体系；保留当前聊天实际结果与 PR 链接，其他成果展示仍遵循长期愿景。
- 内部 HTTP/Worker 重建、宿主机命令回退、全新编排框架、通用事件总线。
- 附件存储、认证、推送和幂等机制的范围外重写。
- 删除真实历史数据、清空持久环境、生产部署、自动 Git 交付或未经要求推送。

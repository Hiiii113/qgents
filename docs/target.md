# Qgents 产品愿景

这份文档记录我们共同讨论、已经确认的产品方向。它是持续更新的协作依据：修改系统、执行任务和日常讨论时，都应先对齐这里的目标，再决定做什么、为什么做。

本文描述的是希望系统成为的样子，不代表所有功能已经实现。用户的新要求优先；讨论产生新的共识时，应及时更新本文，并同步修正 `AGENTS.md` 中被替代的约定。

## 一句话目标

Qgents 提供简单的 **IM 聊天 + GitHub 集成 + 云端 Harness**。用户在群聊讨论需求，Agent 从聊天中获取有效上下文，在用户要求时开展任务，通过工具选择工作环境、操作仓库，并自行组织和返回成果。

系统提供能力与执行环境，Agent 根据用户目标决定如何使用这些能力。保持各部分解耦，代码清爽、行为容易理解，先把功能做成可用的产品。

## 用户的使用过程

1. 用户注册，创建团队或加入团队。
2. 团队新建项目，按需导入多个 GitHub 仓库。
3. 每个项目默认创建一个群聊，不区分主群和需求群；成员在群中自由交流需求、问题和想法。
4. 普通消息用于 IM 聊天，不自动触发 Agent；用户通过 `@Agent` 请求回答、分析或执行工作。
5. Agent 获取相关上下文并进入 loop。纯问答、RAG、聊天检索等不需要仓库工作目录的工具，不自动生成 Task，也不创建沙箱。
6. 首次调用需要仓库代码执行环境的工具时，开启或继续 Task，按需创建沙箱并挂载已选择的 Workspace；未选择时新建 Workspace，随后操作仓库、修改代码并检查结果。同次工作后续工具复用已准备的环境，不逐次创建。
7. Agent 根据实际成果决定回复文本、Diff 卡片、MR 卡片、链接或其他适合的结果。检查没有问题后，可以根据用户的任务目标直接提交 MR/PR。

## 三部分的职责

| 部分 | 提供什么 | 谁决定如何使用 |
| --- | --- | --- |
| IM 聊天 | 团队与项目中的交流、消息与附件、历史检索、Agent 可用的上下文 | 用户决定讨论内容；Agent 按需提取相关信息 |
| GitHub 集成 | 项目仓库导入，以及仓库、分支、提交、推送、MR/PR 等附加能力 | 用户导入仓库；Agent 通过能力操作 GitHub |
| 云端 Harness | Agent loop、工具调用、Workspace、命令与文件操作、执行反馈 | Agent 选择环境、操作顺序和必要的子 Agent |

IM 不承担固定的研发流程调度。GitHub 集成不承担后台自动交付。云端 Harness 是 Agent 的主要工作区域，能够在不启用 GitHub 集成时独立使用。

## GitHub 仓库：导入，而不是自动绑定执行

- 产品中的用户操作统一使用“导入 GitHub 仓库”的表述。项目可以导入多个仓库，方便用户查看，也为 Agent 提供可选择的仓库信息。
- 导入是显式的用户操作，不等于自动 clone、创建分支、创建 Task 或分配 Workspace，也不把仓库固定绑定给某个 Task 或 Workspace。
- 团队通过 GitHub App 安装与授权连接 GitHub，用户从安装已授权的仓库中选择并导入项目。保留 App 安装、回调和授权管理，不提供个人 OAuth；Agent 可使用 App 安装凭证操作仓库和 MR/PR。
- Agent 可以从导入的仓库中选择需要操作的仓库；仓库导入清单不成为 Agent 工作环境的硬性仓库映射。
- GitHub 能力主要交给 Agent 使用。系统提供授权、能力配置和必要的展示入口，实际操作通过工具完成，不在业务代码中预设自动建分支、自动提交或自动创建 MR 的流程。
- clone 时没有指定基线，就使用仓库的远端默认/base 分支；是否创建工作分支，以及后续 commit、push、MR/PR，都由 Agent 根据任务目标决定。

### Skill、MCP 与 Tool 的方向

用户关注的是 GitHub 能力可以附加给 Agent，以及系统与 GitHub 操作解耦，不要求采用某个技术名词。

- **Tool** 是 Agent 真正执行操作的入口，例如查询仓库、clone、执行 Git 命令、创建 PR。
- **Skill** 描述什么时候使用能力、怎么完成工作以及需要注意的约定，可以指导 Agent 组合工具。
- **MCP** 是接入外部工具服务的一种方式；有实际接入或复用需求时再使用。

当前先沿用已有 Tool 机制提供 GitHub 能力，按需补充 Skill；不为了形式同时引入全新的 MCP 平台、插件市场或固定交付框架。后续选择由实现需求决定，保持能力可选、可替换，不让它变成 IM、Task 或 Workspace 的业务前提。

## Task 与 Workspace 独立

**Task 表达要完成的工作；Workspace 提供实际工作的环境。** 两者不应固定一一对应。

- Task 记录工作目标、进度和结果。用户可要求创建任务；Agent 首次实际调用需要仓库代码执行环境的工具时，也会开启 Task，不要求用户另外执行一次“创建 Task”。
- Workspace 是独立资源；创建 Task 本身不分配环境。代码工具首次需要环境时，才准备 Workspace 和 Sandbox，默认在未选择环境时新建工作区，Agent 已选择已有环境时直接复用，不能恢复 Task 与 Workspace 的固定一一绑定。
- 执行记录可以注明使用过哪些 Workspace，便于追踪和继续工作；这种关联不等于固定归属或强制生命周期绑定。
- 继续任务时，Agent 根据上下文和环境状态选择适合的 Workspace；可复用已有环境，不强制新建。
- 同一 Workspace 可以用于后续不同任务；一个任务也不应被模型结构限制为只能使用一个 Workspace。具体使用由 Agent 按实际需要决定，不提前引入复杂调度。
- Workspace 中需要哪些仓库、目录和分支，由 Agent 通过工具管理。系统不自动绑定仓库，也不随 Task 结束自动销毁环境。
- 提供清晰的 Workspace 管理、文件操作、命令执行等工具，让 Agent 获得真实输出和错误，并据此继续工作。

## 上下文与 Agent 工作方式

- 深度重构从聊天消息字段和调用链开始：发送消息只携带基础 IM 所需的内容、提及、回复及消息标识，不附带 Task、仓库、分支、Workspace、沙箱等执行配置。
- 消息持久化后，只有提及 Agent 才启动 loop。工具是否需要仓库代码环境决定是否准备沙箱；不能因为 @Agent 或调用任意工具就创建沙箱。
- RAG、聊天检索以及不依赖仓库工作目录的 grep/检索能力可以直接调用；针对本地仓库文件的 grep 或命令属于需要代码环境的工具。按实际依赖区分，不按工具名称区分。
- 群聊既是用户讨论需求的地方，也是 Agent 获取有效上下文的地方。聊天中提到一个想法，不代表用户已经下达执行指令。
- Agent 按需读取相关消息、附件、项目资料、导入仓库信息、Skill 和 Memory，提取工作目标、约束和已有结论；不把所有历史无差别塞入每次调用。
- Memory 也提供给 Agent 操作和更新的 Tool，与 MR/PR 等能力一样由 Agent 按需调用，不能只作为用户管理的知识库或被动注入的上下文。
- 默认使用通用 Agent，也支持直接指定 Agent。模型决定自己完成还是调用 subagent，不强制经过计划、编码、测试、审查等固定阶段。
- 沿用项目自己的 Agent loop：调用工具后继续，无工具调用的文本回复结束本次运行，设置轮次上限。
- 系统提供执行能力，Agent 决定操作流程；工具反馈必须真实，结果只能描述实际完成的操作与验证。

## 成果展示与 MR

- 成果由 Agent 组织返回，系统提供消息和结构化卡片的渲染能力。
- Diff 卡片、MR 卡片按 Agent 需要输出，不在每次运行结束时由后台固定生成，也不要求所有任务都交付同一种结果。
- Agent 根据修改内容选择合适的检查方式；检查没有问题后，可按用户任务目标调用 GitHub 能力提交 MR/PR，不增加强制的阶段流水线或额外确认步骤。
- 没有代码修改的任务可以只返回分析、说明或其他成果，不强制产生分支、提交或 MR。
- 系统不自动 commit、push 或创建 MR，也不维护一套替代 GitHub 的交付状态机。

## 当前实现与愿景的差距

截至 2026-10-01，已具备项目唯一默认群聊、普通消息与 `@Agent` 的区分、自有 Agent loop，以及绑定在 Agent 上的可选 GitHub Tool。

本次已完成：

- 消息只保留基础 IM 字段；回复统一使用 `replyToId`，删除 QUOTE、replyText 及引用摘要兼容逻辑。
- Task 不再保存固定 workspaceId；独立创建、列出和选择 Workspace，创建 Task 不分配环境。
- 删除 prepare_workspace 前置流程。代码工具首次调用按需开启 Task、挂载 Workspace 和启动 Sandbox；默认新建，Agent 可选已有环境复用或切换。
- 问答、Skill、聊天检索和远端 GitHub API 不启动代码环境；GitHub 凭证不可用只影响调用该能力。
- AgentRun 和 Worker 执行记录追踪实际环境；运行结束释放 Sandbox、保留 Workspace。Task 成果和进度由 update_task 更新，不跟随 AgentRun 自动结束。
- 聊天上下文保留消息 ID 和回复关系，支持工具读取消息全文。
- 消息重试命中已有 clientMessageId 时只返回原消息，不重复启动 Agent 或发送提及通知；提及处理仅由新建用户消息触发。
- 恢复团队 GitHub App 安装、一次性回调、安装同步和解除连接；支持从 App 授权仓库中选择并导入项目。Agent 的 github-app 能力按当前项目导入记录获取仓库级短期安装凭证，支持 Git 和 MR/PR 操作；安装与仓库授权变化通过 Webhook 同步。不提供个人 OAuth。
- 精简 Memory 模块：删除无引用的消息关系实体与检索方法，复用数据库字段映射和状态事件发送，管理员手动创建改为一次写入；同步清理过时和重复注释，保留现有接口、审核流程及上下文预算。
- 精简 Notification 模块：合并设备注册与更新的重复赋值，使用 Lombok 构造器注入，删除未调用的事件清理方法，修正旧通知类型和重复注释；保留通知中心、实时提醒、FCM 推送及重试行为。
- 精简 Realtime 模块：项目、团队和通知 SSE 共用游标校验、连接生命周期、轮询与心跳；删除无用的推送包装和群参数，更新旧机制注释；保留 WebSocket、SSE 接口、权限与过滤、事务提交后推送和项目事件重试。

仍需后续实现：

- Memory 的 Agent 操作和更新 Tool 尚未实现；目前只有用户管理接口和已批准内容的上下文注入。
- GitHub App 与仓库导入已实现后端接口和工具，仍需前端接入及真实 GitHub 环境联调。
- 提供由 Agent 按需返回的 Diff/MR 等结构化成果，并接通聊天展示。
- 继续整理上下文按需读取、重复开发命令工具与失效项目设置。

RAG 和代码索引检索尚未实现；本次明确它们无需沙箱的接入方式，不把预留方向描述为已上线功能。

## 持续维护方式

- 开始修改系统或讨论产品方向前，阅读本文及 `AGENTS.md`，检查方案是否与愿景一致。
- 讨论确认新的长期要求后，更新对应章节；被明确替代的旧要求应修正，避免同时保留相互矛盾的指令。
- 区分已经确认的方向、仍需讨论的设计和实际实现状态。没有达成共识的建议不能写成用户已经确定的要求。
- 完成功能后同步更新“当前实现与愿景的差距”，让本文既能指引方向，也能帮助判断下一步该做什么。
- 与用户共同完善系统，不擅自把“提供一种能力”改成“系统自动替用户执行一套流程”。
- 代码注释随实现同步更新，用直接易懂的文字说明用途、行为和必要原因；清理过时注释及“契约 §…”等不清晰的章节引用。
